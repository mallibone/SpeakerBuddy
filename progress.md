- `JsonStringEnumConverter<BeatType>` alone serializes enum members using their C# name ("Talk"/"Demo"), not the source-gen `PropertyNamingPolicy` (that policy only governs property names, not enum converters). Added a tiny `BeatTypeJsonConverter : JsonStringEnumConverter<BeatType>(JsonNamingPolicy.CamelCase)` subclass instead, since a `Type[]` converter list can't pass constructor args inline.
- Added `DefaultIgnoreCondition = JsonIgnoreCondition.WhenWritingNull` to `TalkJsonContext` — without it, re-serializing an object with absent optional fields (e.g. a talk beat's null `Steps`) writes explicit `null` properties that don't exist in hand-authored input JSON, breaking structural round-trip equality. Not explicitly called out in plan.md but required for the round-trip test it prescribes.
- `TalkImporter.ImportFromJson` → implemented as `ImportFromJsonAsync(string json, CancellationToken ct = default)`. Plan's signature omits Async/CancellationToken, but the method awaits `ITalkRepository.SaveAsync`, so it must be a `Task`-returning method; named per C# async convention and threaded a `CancellationToken` through for consistency with the repository interface.
- `TalkId` derivation (slug + 8-char content hash) hashes the raw input JSON string (SHA-256, first 8 hex chars), not a canonicalized/re-serialized form — "same content" is interpreted literally (same pasted bytes re-imports to the same id); a reformatted-but-semantically-identical JSON paste would get a new id. Not spelled out in plan.md; flagging in case that's not the intended semantics.
- xUnit v3 analyzer (`xUnit1051`) requires every test that calls an async method with a `CancellationToken` parameter to pass `TestContext.Current.CancellationToken` (enforced as an error via `TreatWarningsAsErrors`). Adopted a `private CancellationToken Ct => TestContext.Current.CancellationToken;` convenience property in test classes that touch `ITalkRepository`/`TalkImporter` — keep using this pattern in later test classes that call cancellable Core APIs.
- Resolved the pace-calculation ambiguity plan.md §3.2 flagged (and said to escalate on if it "actually bites"): `LiveTalkEngine` uses `Timeline.Sum(PlannedDurationMinutes)` — not `Session.PlannedDurationMinutes` — as the single "total planned" denominator for `Remaining`, `OverallProgress`, and the final-beat pace check. Rationale: pace/position math is inherently beat-granular (`PaceCalculator` already takes "cumulative planned at position" built from beat sums), and the two totals can differ (that's exactly what the validator's duration-mismatch warning is for) — mixing beat-sum position math with a session-level denominator for progress/remaining would produce a progress bar that doesn't reach 100% (or overshoots) exactly when the talk finishes. Didn't escalate to Fable: the decision is fully contained inside `LiveTalkEngine`/`PaceCalculator`, is unit-testable (see `FinishDetection_AfterLastBeat` asserting `OverallProgress == 1` exactly at completion), and doesn't ripple into other files — below the plan's §7 bar for escalation.
- `Back()` beat-boundary semantics (not fully spelled out in plan.md): crossing back into a previous beat (a) resets that beat's "started at" timestamp to now, so if the speaker later re-advances past it, `BeatTiming.Actual` reflects only the time spent on the *replay*, not the original visit — kept simple deliberately (the engine has no timestamp stack); and (b) lands on the *last* step if the previous beat is a demo beat (re-showing "what I was just about to advance past" reads as the more useful default for a misclick-recovery gesture than restarting the beat's steps from 0). `Back()` also does not remove or edit an already-recorded `BeatTiming` for a beat you've stepped back into — timings are append-only, written only on forward transitions.

- **New gotcha, worth remembering for every future live-verification pass:** `dotnet build src/StageBuddy.App -f net10.0-ios` (no `-t:Run`) only rebuilds the `.app` bundle under `bin/`; it does **not** reinstall it into the simulator. Relaunching via `xcrun simctl launch` (or even `terminate` + `launch`) after a plain build just re-runs the **already-installed, stale** copy — the UI silently shows old behavior with no error, which cost real time to diagnose (looked like a MauiReactor bug at first) during M3.6 verification. Fix: after a plain build, explicitly `xcrun simctl install <udid> <path-to>.app` before `launch`. (`-t:Run` avoids this entirely by installing itself, but the playbook's own advice to avoid combining build+run still stands for other reasons — split into plain `build`, then `install` + `launch`, not `build -t:Run`.)
